# Backlog

Every open item across this repository's documents, condensed to one line each with a pointer to
where it is argued in full. Nothing here is new analysis — it is an index of decisions and work
that are already written down and not yet done, so a session can start from a list rather than a
re-read.

Status vocabulary: **defect** — the code is wrong; **decision** — nothing is wrong until someone
chooses; **work** — agreed, designed, unbuilt; **gap** — untested or unmeasured.

Every row here is open. What was fixed and why is recorded in the change log of the page that owns
it, which is also the page the **Where** column names — a finished item kept on two pages drifts on
one of them, and this one had drifted.

## A. Correctness defects

| # | Item | Where |
| --- | --- | --- |
| A19 | **Two validators the mod never calls.** `BlockThermalProperties.Validate()` returns, in its own words, "problems a mod author would want to hear about" — a zero specific heat, an emissivity above one, a waste fraction that creates energy from nothing — and `ThermalSettings.Validate()` is its counterpart for world settings. Neither is called anywhere under `Data/Scripts`; the only callers are three test classes. So the diagnostics are correct, tested, and have never been seen by an author or an administrator. Wire them or delete them. | [rules.md](rules.md) `D2` |
| A4 | **`SweepRoomPressure` is the one whole-grid pass that is not a rota or a budgeted slice.** Two game API calls per compartment every eight steps, bounded by compartment count rather than block count. Measured at 0.054 % of real time on twelve compartments, so the rota is deliberately deferred: it is a station-scale risk with no evidence behind it, and the sweep is now timed with counters so the next dump from a large station answers with a number. | [known-issues.md](known-issues.md#open-defects) |
| A17 | **The shipped defaults diverge on a burning 4,000-block ship with 0% of their substeps refused.** `x-burning-ship` passes 10,000 K and never settles. Starvation was the published explanation and is falsified: `candidate`, refused 49% on the same rig, lands one kelvin away. The cause is unknown, so the next step is to find it rather than to fix it — `MaxSubsteps` is already granted in full. Pinned by `ProfileSuiteTests.TheShippedProfileStillDivergesOnABurningShip`. | [known-issues.md](known-issues.md#open-defects) |
| A16 | **A buried grid convects with the planet's air coefficient.** Nothing under the surface is against air, but rock contact is not modelled, so the environment exchange stays at `PlanetConvectionCoefficient` — 50 W/(m²·K) at 20 km down. Ambient is right there (the rock's own temperature) so the direction of the exchange is right and the rate is a guess. What it should be is a conduction against rock, which needs a contact area the model does not compute. Visible on `-- descent`. | [environment.md](environment.md#underground) |
| A9 | **Solar occlusion by planets and asteroids is per grid**, so a capital ship crossing a terminator ramps rather than switching but never carries a shadow edge across its own hull. Filed as a deliberate limit; a per-block implementation exists, commented out, which makes it a decision that was taken and then half-unmade. | [known-issues.md](known-issues.md#deliberate-limits) |

## B. Player-facing gaps and decisions

| # | Item | Where |
| --- | --- | --- |
| B4 | **Block temperatures are not reconciled between server and clients.** Settings and the two pump throttles replicate, and `/thermal sync` compares a client against the server by digest; temperatures do not. Clients re-simulate from the same inputs and drift, and a client joining mid-session starts from saved values. Damage is server-only, so the divergence is cosmetic — but how far a client may drift before it is corrected is undecided. | [known-issues.md](known-issues.md#open-defects) |
| B8 | **Three things are left on the settings surface**: Status as the mod's own report rather than a list of what changed, the config file regrouped by system with a migration off the flat shape, and per-subtype block overrides for the 432 values in `Cubes.xml`. | [configuration.md](configuration.md#where-the-settings-surface-is-going) |
| B9 | **A startup crash in `ThermalGrid.Tick`, seen once and not reproducible.** The tick is guarded and logs its inner frames, and faults record whatever the collection state, so a recurrence names itself rather than taking the session down or being discarded with telemetry off. Watching, not chasing. | [telemetry.md](telemetry.md#faults-are-recorded-whether-or-not-collection-is-running) |
| B5 | Radiators cannot be inline loop segments — no coolant ports of their own, so a loop cannot run through one. Adding ports needs the port geometry checked against the 1×5×2 model. | [known-issues.md](known-issues.md) |
| B10 | **A player in an extremely hot room takes no damage.** The suit is assumed to regulate both ways, burning energy to do it, so Keen's own energy-drain modifiers want disabling first; past a suit thermal limit the regulation fails and the player is damaged, and an open helmet is unsafe at temperatures a closed one survives. Nothing exists today — `ThermalHud` is the only place the mod touches `IMyCharacter`, and room air already carries the temperature to test against. | new |
| B11 | **A debug block that emits heat like a small sun,** for validating the point-source path in game: terminal-configurable output in watts, falling off with distance. The falloff is already there and already realistic — `ThermalHeatSources` resolves `P / (4πr²)` with a range cutoff — so this is a block with a slider that registers itself through the same path the mod API uses. | [api.md](api.md#heat-sources) |
| B14 | **The wind's meridional component is poleward everywhere and reverses across the equator.** Air diverges from the equator — Earth's trades converge — and the vector flips end for end at latitude 0. `TheWindSwingsThroughTheCalmsRatherThanReversingAcrossALine` exists to prevent exactly this and measures only the east component, so it passes. Nothing tests the north-south half of `WindField.Direction` at all. | [environment.md](environment.md#limits-and-open-questions) |
| B16 | **Roughness length is one number for a whole world.** The ground material under a grid is already classified for the temperature model, and roughness is exactly what it should vary with — snow smooth, forest rough. `WindRoughnessLength` is a world setting instead. | [environment.md](environment.md#what-the-solver-computes) |
| B17 | **A parked grid can be pushed over the friction threshold by wind alone.** 4.2% of field samples exceeded `FrictionAtSpeedsAbove` at 50 m/s; the offline storm scenario reaches **209 m/s with 19% of samples over the threshold and 49% over the engine's own ceiling**. This is the defect the wind field was originally built to prevent, reopened by the vertical profile multiplying the band share above the reference height. `AParkedShipIsNotFlying` cannot see it: it tests `WindField.Speed` alone, not the composed model. The fix is a balance call — cap the composed speed at the ceiling, lower the storm fraction, or accept that a storm at 150 m is genuinely violent. | [environment.md](environment.md#measuring-it) |
| B18 | **The engine's figure is no longer a ceiling.** 3 field samples exceeded it (80.3 m/s against 72.9) once profile and band share compound. The whole justification for using `GetWindSpeed` was that it bounds the wind; it now only scales it. Decide whether to reinstate the bound. | [environment.md](environment.md#wind-the-whole-of-it) |
| B19 | **Every terrain factor saturates its cap on ordinary SE ground.** SE hills reach 12% of a planet's radius against Earth's 0.14%, so terrain is ~80× steeper than the wind-engineering literature the caps came from. Speed-up, shelter and channelling all run into their limits on every shipped world at every size — the caps are doing the modelling rather than bounding it. Worth re-deriving them for SE slopes rather than terrestrial ones. | [environment.md](environment.md#world-size-and-why-every-borrowed-constant-lands-oddly) |
| B20 | **The shipped boundary layer is taller than several shipped atmospheres.** `WindGradientHeight` is 600 m; Titan, Europa and the Moon have atmospheres 285–570 m deep, and Triton's peaks stand above its air entirely. The profile is being evaluated in vacuum and only the ceiling reaching zero keeps it sane. A per-planet gradient height derived from `AtmosphereAltitude` would be the honest fix. | [environment.md](environment.md#world-size-and-why-every-borrowed-constant-lands-oddly) |
| B22 | **Seven of the eight shipped worlds have air density exactly 1**, so swing, pole drop, lag and convection derive to the same figure for all of them — only the airless Moon differs. Gravity (lapse rate) and solar protection are the only real differentiation between atmospheric worlds. Whether to author density per world in this mod's own file, against the engine's, is open. | [environment.md](environment.md#limits-and-open-questions) |
| B23 | **`GetTemperatureInPoint` returns zero wherever there is no oxygen**, so the `game_temperature` telemetry column is flatly zero on Mars, Europa and the Moon. It is a 0..1 comfort figure rather than kelvin in any case. **Measured**: over 3,465 breathable rows it correlates +0.86 with the sun's elevation and +0.12 with this model's ambient, so it is a daylight figure and not a cross-check on anything thermal. The telemetry should say so where it is reported. | [environment.md](environment.md#temperature-two-things-and-neither-is-a-temperature) |
| B24 | **A thermal camera view, and no known way to build one.** Mods get no shader, no post-process and no frame buffer; blanking the world and redrawing every body as a billboard gives coarse terrain, discs for asteroids and nothing for what the mod does not draw, which is why the first heat overlay was removed. **Wanted, and the route is expected to be indirect** — whether any shader or material parameter is reachable at all, transparent materials as the extinguisher overlay already uses, particle effects as a rendering surface, and per-block emissive, which is the one path the engine definitely exposes. | [document-of-intent.md](document-of-intent.md#thermal-vision--wanted-method-unknown) |
| B25 | **No feedback reaches a player who is not looking at an instrument.** No sound emitter, no particle effect and no emissive code exists anywhere in the mod. Intent is subtle and in-world rather than an alarm: metal ticking and pinging as it expands, joints under a gradient, air distorting around a hot block in atmosphere, and a block glowing as it climbs. The trigger is a ratio the solver already computes every step. **Shape decided**: audio is cockpit-only, a lead cue about three seconds out and a distinct one at the crossing; visuals are a linear ramp keyed to each block's threshold temperature, full at critical and gone at ordinary temperatures. **Still open**: the cue itself, and that a linear projection from `LastDeltaTemperature` over-warns on a block that is levelling off. It is also the first presentation feature meant to be on by default, so its cost when nothing is hot must be a threshold test and nothing more. | [document-of-intent.md](document-of-intent.md#natural-feedback--not-built) |
| B26 | **The readouts should be indistinguishable from the game's own HUD.** They are drawn through Rich HUD so they can adopt its placement, scaling and styling; the goal is that a player reads a temperature the way they read a power figure, with nothing mod-shaped announcing itself. No check covers this and none obviously can — it is a judgement made by looking. | [document-of-intent.md](document-of-intent.md#instruments--built) |

## D. Performance and scale

| # | Item | Where |
| --- | --- | --- |
| D18 | **The relaxation row is all ones for ninety-five per cent of nodes and is written for all of them.** Skipping the divide for the unbound ones was tried, is exact, and measured as nothing against a 4-6 % run-to-run spread — so the row's ~1 ns a node is the two loads and the store, not the arithmetic. A future attempt should aim at not writing the row: the conduction loop reads it per link end regardless, so this needs a sparse representation or a per-grid flag rather than a cheaper sum. Only live when a grid is refused the substeps it asked for. | [benchmarks.md](benchmarks.md#the-relaxation-rows-cost-is-the-row-not-the-divide--tried-and-dropped) |
| D13 | **A grid is visited every frame whether or not the frame does solver work.** `bench smallgrids` now measures that visit on its own — 5.9 ns a grid a frame, flat with grid size, 24 % of what a one-block grid costs and 70 % of its pacing overhead. No change to a step can reach it; only visiting fewer grids per frame can. | [benchmarks.md](benchmarks.md#below-eight-hundred-blocks) |
| D14 | **Spreading a step costs a large grid 5-13 % in cache.** Between two of its frames the other grids in the world evict its arrays, so every resume is a cold start. Staggering whole steps across frames instead would keep each grid's data hot and cost one dispatch, at the price of a lump per grid — the trade the current design was chosen to avoid, and worth re-deciding now the lump is measurable. | [benchmarks.md](benchmarks.md#below-eight-hundred-blocks) |
| D15 | **A frame spikes to 68 ms every thirty seconds and nothing says why.** Five frames of the 2026-08-20 fleet dump, evenly spaced, each reporting 2.0-2.8 ms of solver and zero topology, rooms and exposure against a 67-72 ms total. Nothing in the mod runs on that period — the mass sweep is 8 steps and the hottest-node scan 4. The environment sample and the after-step observation are now timed and the cost table carries an `unattributed` row, so the next dump attributes it or narrows it to pacing. | [telemetry.md](telemetry.md#what-the-stages-leave-over) |
| D19 | **Nothing is threaded, and the intent is that as much as possible should be.** Use as much of the CPU as possible while taking as little of the game thread as possible; the two halves are one goal, since the game's simulation stability is set by what runs on its own thread. The solver is already safe to split — order independence is an invariant, not an accident — and `MyAPIGateway.Parallel` provides `For`, `ForEach`, `Do` and `Start`. The natural shape is *solve in parallel, apply on the game thread* via `InvokeOnGameThread`, because reads must not race the game mutating a grid. **Measure before adopting, and note the two figures point opposite ways**: 8,000 blocks solve in 0.128 ms a step, possibly under the cost of a hand-off, while a 242-grid fleet spent 25.9 % of real time in the solver. Per-grid parallelism across many grids is a different change from splitting one huge grid, and the fleet figure argues for it first. | [document-of-intent.md](document-of-intent.md#use-the-machine-and-stay-off-the-game-thread) |
| D1 | A solver step is atomic and 118 ms at a million blocks, down from 623 ms. A step must touch every node, so only activity tracking, chunking and multirate make it smaller; all designed, none built. Whether what is left is near the memory-bandwidth floor is now an open question rather than an answer — the last time that was claimed, two passes were reaching through the node objects instead. | [scale-design.md](scale-design.md), [load-and-hitching.md](load-and-hitching.md#what-is-still-open) |
| D2 | The room map floods the bounding volume — 14× the block count on a hull — and takes 7,207 ticks (twenty minutes) to converge at a million blocks. Wants the host gas system, with a coarse flood as fallback. | [scale-design.md](scale-design.md) §4 |
| D3 | World load is 11 s at a million blocks in one call. Acceptable behind a loading screen; a blueprint pasted mid-session takes the same path. | [load-and-hitching.md](load-and-hitching.md#what-is-still-open) |
| D4 | The first step of a grid's life spikes on first touch of every flat array: 28.3 ms above a 13.2 ms tick at half a million blocks, and 53 ms above a 26 ms tick at a million. A warm-up rather than a stutter, and still the largest number in the distribution at the top rung. | [known-issues.md](known-issues.md) |
| D5 | Lumping (merge a stiff node into its dominant neighbour at topology time) — exact where the substep cap is approximate, and removes links as well as stiffness. Worth a few per cent on SE1 fleets; the design work is unlumping incrementally on change. | [stiffness.md](stiffness.md#2-lumping--the-same-idea-done-properly) |
| D6 | Multirate stepping, and implicit integration as the endgame. Both currently lose to the per-block cap on an SE1 fleet; both are the answer when the stiff set is not a thin tail, i.e. SE2. | [stiffness.md](stiffness.md#3-multirate-stepping--when-the-tail-is-not-thin) |

## E. Memory

Local changes, no design work behind them, ~20 % of a grid's footprint between them.

| # | Item | Saving |
| --- | --- | --- |
| E1 | Drop the solver's `nodesByKey` dictionary; `BlockInstance` carries the node index. | ~36 B/block |
| E2 | Pack the per-node face data — `int[6]` counts into one packed int, weights derived, sun-lit array only when self-shadowing is on. | ~70 B/block |
| E3 | **Room cells are held twice**, once per room and once in `roomIndexByCell`. One `Vector3I[]` sorted by room with an `int[]` of range starts holds both at 12 bytes a cell — but the dictionary answers `RegionOf` on the exposure path, so this means giving that lookup a different shape rather than deleting it. | ~9 MB at 126k, 47 at 500k |
| E4 | Move the node diagnostics out of `ThermalNode` into a side array allocated when diagnostics are on. Their *write* cost is settled — the figures are written on the last substep alone — but the fields still sit on every node whether or not anything reads them. | ~24 B/block |

# Overheating glow

This page covers the natural overheating visual, its rendering limits and reproducible checks.
It does not change thermal simulation, damage, the warning band or thermal-camera rendering.

## Design and acceptance criteria

The replacement uses a smooth radial core and halo in one depth-tested, additive billboard per
visible exposed face. The texture must have zero RGB and alpha on every border, radial symmetry,
a monotone falloff and reproducible mipmaps. A face must fade continuously to zero at grazing
angles and at the 2,000 m draw boundary. Size and surface offset must scale with grid size.
The existing Planckian colour and linear last-100-K warning ramp remain authoritative.

The renderer must submit no more than 4,000 quads per frame, including many-grid scenes, and hold
no more than 32 nearby heat lights. Disabling HeatGlow or unloading must release every light;
dedicated servers must do no rendering. Per-face calculation must allocate zero managed bytes
once warmed. These are deterministic work and allocation bounds, not a claim about GPU time.

Offline acceptance requires the full solution to compile, focused presentation and existing heat
cue tests to pass, asset regeneration to match byte-for-byte, and documentation checks to run.
Visual acceptance additionally requires a live game check: small and large armour, slopes and
functional blocks; isolated and adjacent hot blocks; cold/half/full ramp; frontal/grazing views;
bright and dark scenes; cockpit, occlusion, cooldown, switch-off and world unload. No offline
preview can certify game bloom, whitelist acceptance or the appearance of transparent geometry.

## Rendering contract

[HeatGlowStyle.cs](../Data/Scripts/Thermodynamics/Presentation/HeatGlowStyle.cs) holds view shaping
in the presentation library. [ThermalGlow.cs](../Data/Scripts/Thermodynamics/ThermalGlow.cs) consumes
it from the existing session Draw hook; the existing grid cue pass supplies temperatures and
exposed faces, and the existing unload hook clears lights. There is no new solver pass, network
packet, setting, particle emitter or model edit.

For normalised texture coordinates x,y in [-1,1], let q = x²+y². The intensity is zero for q >= 1,
and otherwise `(0.72 exp(-5q) + 0.28 exp(-1.5q)) (1-q)²`. The two lobes supply a compact hot core
and a wider halo; the polynomial makes the value and slope zero at the support boundary. This
is an authored visual profile, not a fitted temperature distribution. The generator stores
sRGB-encoded intensity in RGB and linear intensity in alpha, consistent with premultiplied colour
sampled through an sRGB texture view. Actual game texture/view handling remains a live check.

The shipped RGBA8 DDS is 128×128 with eight mip levels and is **87,508 bytes including its header**.
Mip averages are computed in linear space. Every mip's border is set to zero; the last 2×2 and
1×1 levels are transparent so subpixel patches vanish instead of becoming bright squares. The
asset is regenerated by [build_texture.py](../tools/thermal-glow/build_texture.py), using only the
Python standard library. No image-generation service or copied art is involved.

The patch half-extents are 1.12 times the block's face half-extents. Its offset is 0.008 times
the grid cell size: 4 mm on small grids and 20 mm on large grids. Premultiplied colour is multiplied
by warning brightness, a 0.7 surface gain and both fades; the RGB ramp is applied once. Facing uses
smoothstep over outward view cosine 0..0.25, and distance uses the reverse smoothstep from
1,600..2,000 m. The material is unlit and depth-tested in the existing AdditiveBottom pass; there
is no PostPP or IgnoreDepth bypass and no artificial flickering of steady heat.

Lights keep the existing 2.5 maximum intensity and 120 m range cap. They fade over the last 40 m
of a 200 m distance measured from the light's influence sphere, and are removed beyond it. Grids
outside the 2,000 m drawing sphere skip both block drawing and light reduction. Quads remain
bounded by one shared remaining budget; light creation checks the live dictionary count against
32. Lights are released after cooling, grid removal, range exit, missing camera, switch-off and
unload. At saturation, departing lights are retired after traversal, so a new light can wait one
frame for its slot. These lifecycle statements are code inspection, not executed engine tests.

## References and evidence

* [WeaponCore-StarCore](https://github.com/StarCoreSE/WeaponCore-StarCore), inspected at
  commit `98ce92d32037fd361a676494e5e3cc1bdd1ff6ab`: WeaponController writes the named Heating
  emissive on configured parts. This supports temperature-driven emissives where a model provides
  them, but cannot give arbitrary armour a new emissive material. No source or assets are copied.
* Workshop item `571920453`, supplied local installation: SEDrag.MyLightMethod creates a heat
  light and CloseLight removes it. The replacement keeps pooled lighting and avoids the reference's
  per-light shadow/reflector cost. No source or assets are copied.
* Installed SE1 Content/Shaders/Transparent/Billboards.hlsl multiplies texture RGBA by billboard
  RGBA; Transparent/OIT/Globals.hlsli passes premultiplied colour through for non-OIT rendering.
  The glow asset therefore carries falloff in RGB as well as alpha: white RGB with soft alpha alone
  is insufficient evidence that an additive quad has no rectangular edge.

## Limits

This is a soft surface cue, not a radiometrically calibrated blackbody renderer. Brightness is a
warning keyed to each block's critical rating, as specified in document-of-intent.md; the radial
profile and view fade are artistic approximations. Exposed bounding faces do not conform to slopes,
curved meshes, holes, deformation or animated subparts. Soft borders and grazing fade suppress the
box silhouette but do not create mesh emissivity. Adjacent patches can overlap. A shadowless light
can leak through walls and a single grid light cannot represent disconnected hotspots accurately.
Submission/light limits can omit geometry or lights; grid iteration order is not a nearest-first
sort. These caps do not bound CPU scans: nearby lit-block traversal and light-region reduction
remain linear in the available cue lists. The 1.12 halo scale expands quad area by 25.44% relative
to the former face fill, so equal submission count does not imply equal GPU cost. There is one
texture sample per fragment and no added billboard layer, but only a paired game measurement can
establish the resulting frame-time change.

## Live verification procedure

In a disposable local server world, aim at each specimen and use the existing `/thermal heat`
command to set its critical temperature; the reply names the rating. Use `/thermal heat <kelvin>`
with rating minus 101 K, minus 50 K and the rating itself to compare cold, half and full brightness.
The solver continues to evolve temperature, so record actual temperature and capture delay rather
than assuming the command pins it. Damage at the rating can remove the specimen.

Choose specimens by geometry coverage: large and small full armour cubes, a slope, a curved armour
block, a multi-cell functional block and a block with animated subparts. Add adjacent hot blocks
and a hidden hot block behind an opaque wall. Record day/night lighting, camera pose, distance,
FOV, display resolution, graphics/bloom settings, mod revision and game version. Check the views
listed in the acceptance criteria, then cooldown, HeatGlow off/on, grid deletion and unload/reload.
Reject a visible rectangular edge, persistent light after removal, or opaque glow through walls;
report slope/hole mismatch and light leakage as approximation limits rather than calling them
verified realism. Compare GPU cost only in paired same-scene runs with identical settings and
publish repeated samples and their spread as required by rules.md. No such timings are supplied
by this offline result.
